# Paymos для Magento 2

[English](README.md) | [简体中文](README.zh-CN.md) | **Русский** | [Español](README.es.md) | [Deutsch](README.de.md) | [Türkçe](README.tr.md)

Официальный платёжный модуль Paymos для Magento Open Source и Adobe Commerce. Добавляет один способ оплаты в оформление заказа: покупатель создаёт заказ, попадает на страницу оплаты Paymos, выбирает токен с сетью и отправляет перевод со своего кошелька. Magento выставляет инвойс по заказу, когда подписанный вебхук сообщает о подтверждении перевода в блокчейне, а не когда покупатель возвращается в магазин.

## Требования

- Magento Open Source или Adobe Commerce 2.4 — модулю требуется `magento/framework` версии 103.0 или новее
- PHP 8.3, 8.4 или 8.5 (Adobe Commerce 2.4.9 прекратила поддержку 8.1/8.2)
- Доступ к консоли для запуска `bin/magento`
- Витрина по HTTPS: процесс подключения отклоняет базовый URL на обычном HTTP
- Аккаунт Paymos с открытым в дашборде проектом, который нужно привязать

Версии указаны в `app/code/Paymos/Payment/composer.json`. Архив релиза уже включает Paymos PHP SDK в собственной папке модуля `vendor/`, поэтому при ручной установке Composer не нужен.

## Установка

Скачайте `paymos-magento2-<version>.zip` со страницы [Releases](https://github.com/Paymos-labs/magento2/releases/latest) или из раздела **CMS integration** в дашборде Paymos и распакуйте архив в корень Magento. Файлы внутри уже разложены по пути `app/code/Paymos/Payment/…`, переносить вручную ничего не нужно.

```bash
bin/magento module:enable Paymos_Payment
bin/magento setup:upgrade
bin/magento setup:di:compile   # production mode only
bin/magento cache:flush
```

Команда `setup:upgrade` создаёт две таблицы: `paymos_payment_invoice` со снимком для каждого заказа и `paymos_payment_event` — журнал дедупликации вебхуков.

Для каждого релиза собирается единый архив, одинаковый для всех мерчантов. В нём нет ни API-ключа, ни API-секрета, ни ID проекта, ни секрета вебхука, ни OAuth-токена, ни кода устройства — сама установка ничего не подключает.

## Подключение

1. Откройте в дашборде Paymos проект, через который должен работать магазин. Именно этот проект привяжется к магазину — отдельного выбора проекта в модуле нет.
2. В админке Magento перейдите в **Stores → Configuration → Sales → Payment Methods → Paymos** и нажмите **Connect Paymos**.
3. Подтвердите показанные URL магазина и проект в открывшейся вкладке Paymos. Если браузер заблокировал вкладку, в этой же строке появятся ссылка для подтверждения и код пользователя.
4. Дождитесь, пока **Connection status** покажет активное подключение, и переведите **Enabled** в Yes.

Одно подтверждение сразу настраивает Sandbox и Live. Ваш единственный активный платёжный ключ используется повторно — или создаётся новый, если его ещё не было — а вебхук инвойсов регистрируется по адресу:

```text
https://your-store.example/paymos/payment/callback
```

Существующий вебхук используется повторно только при полном совпадении адреса, категории и проекта; конфликтующий вебхук на том же URL никогда не перезаписывается. Авторизация устройства работает как одноразовый канал доставки: короткоживущий токен удаляется, а все дальнейшие вызовы Merchant API подписываются HMAC.

Учётные данные записываются в `core_config_data` в зашифрованном виде через `EncryptorInterface` Magento и никогда не выводятся обратно в админку. Полей для ручного ввода секретов нет: заменить их можно только повторным подключением.

## Область действия настроек

Поля модуля доступны на уровнях **Default Config** и **website**. Витрины (store views) наследуют значения по стандартному механизму Magento, и именно итоговое значение витрины применяется при оформлении и обработке её заказов.

| Настройка | По умолчанию | Назначение |
|---|---|---|
| Enabled | No | Показывать ли способ оплаты покупателям |
| Title | `Pay with crypto (Paymos)` | Название, которое видит покупатель |
| Mode | `sandbox` | Какой набор учётных данных использует сайт |
| New order status | `pending_payment` | Статус, пока покупатель оплачивает заказ |
| Paid order status | `processing` | Статус после подтверждения оплаты |
| Debug logging | No | Диагностические записи в `var/log/paymos.log` |
| Sort order | `1` | Позиция среди остальных способов оплаты |

Учётные данные хранятся на уровне всей установки, а не каждого отдельного сайта, поэтому второму сайту не нужно проходить подтверждение заново. Переключайте сайты между тестовым и рабочим режимами одним полем **Mode**. Повторное подключение требуется только после смены базового URL, отзыва платёжного ключа или ротации секрета вебхука.

## Что происходит с заказом

| Событие Paymos | Результат в Magento |
|---|---|
| Инвойс создан, покупатель перенаправлен | Назначенный **New order status** и комментарий в истории с номером инвойса |
| `invoice.confirming` | Статус не меняется; в комментарий записывается, что перевод подтверждается |
| `invoice.underpaid_waiting` | Статус не меняется; заказ ждёт доплату остатка |
| `invoice.awaiting_payment` | Статус не меняется; учтённый ранее платёж исчез после реорганизации цепи |
| `invoice.paid`, `invoice.paid_over` | Создаётся офлайн-инвойс Magento, заказ переходит в состояние Processing и выбранный **Paid order status**, покупателю уходит письмо с инвойсом |
| `invoice.underpaid` | Заказ отменяется |
| `invoice.expired`, `invoice.cancelled` | Заказ отменяется |

В поле transaction id документа инвойса записывается хеш последней подтверждённой транзакции в блокчейне, а если его нет в данных события — идентификатор инвойса Paymos.

Эту таблицу прикрывают две защиты. Во-первых, если сумма или валюта заказа изменились после создания инвойса, заказ автоматически не закрывается: в историю добавляется комментарий с просьбой проверить вручную, а сам вебхук всё равно подтверждается, чтобы прекратить повторные попытки доставки. Во-вторых, запоздавшие события `confirming`, `underpaid`, `expired` или `cancelled`, пришедшие по уже оплаченному заказу, попадают в лог и отбрасываются без изменений.

## Проверка перед запуском в рабочем режиме

1. Установите **Mode** в Sandbox и оформите тестовый заказ на витрине.
2. Откройте этот инвойс в дашборде Paymos в режиме Sandbox. Кнопки **Pay Full**, **Pay 50%**, **Pay 150%** и **Cancel** запускают те же события жизненного цикла, что и реальный платёж, но переводы в блокчейн не уходят.
3. Проверьте заказ в Magento: статус, комментарии в истории и появление документа инвойса.
4. Переключите **Mode** на Live. Рабочие ключи пришли вместе с тем же подтверждением — заново подключать или настраивать модуль не придётся.

Тестовые события в Sandbox не содержат переводов в сети, поэтому в них записывается ID инвойса там, где в рабочем режиме стоит хеш транзакции.

## Вебхуки

Уведомления приходят `POST`-запросом на `/paymos/payment/callback`. Маршрут освобождён от проверки form key Magento, потому что границей доверия служит заголовок `X-Webhook-Signature`: неподписанный запрос или запрос с неверной подписью получает `401` и не доходит до заказов. Заголовок `X-Webhook-Id` не меняется при повторах и сохраняется в `paymos_payment_event` для дедупликации, поэтому повторная доставка отвечает `200` и ничего не меняет.

Финальные события проходят обратную проверку. Перед завершением или отменой заказа модуль запрашивает инвойс напрямую из Merchant API и сверяет его с сохранённым снимком — расходящиеся данные отклоняются.

Один цикл доставки включает 11 попыток за примерно 16 часов, так что кратковременная недоступность магазина не потеряет событие. В дополнение к этому задача cron `paymos_reconcile_invoices` каждые 15 минут подтягивает из API недавние незакрытые инвойсы, а `paymos_reconcile_refunds` каждую минуту опрашивает ожидающие возвраты; обе задачи требуют работающего cron Magento.

## Возвраты

Модуль поддерживает нативные возвраты через Paymos Merchant API (`/v1/refunds`) в двух режимах:

- `full` — возврат полной оплаченной суммы инвойса;
- `overpayment` — возврат только переплаты по заказу `invoice.paid_over`.

Средства возвращаются исключительно на проверенный адрес кошелька `first_sender`, зафиксированный Paymos при оплате инвойса. Вручную адрес получателя не указывается, а частичные возвраты по позициям или корректировкам отклоняются.

- **Полный возврат (`full`):** откройте инвойс оплаченного заказа Paymos в админке Magento и отправьте стандартный **Credit Memo**, где возвращаются все оплаченные позиции без корректировок доставки и сумм. Плагин `Paymos\Payment\Plugin\RefundEntry` перехватывает отправку, регистрирует возврат `full` в Paymos без преждевременного создания локального Credit Memo и перенаправляет на панель **Paymos refunds**.
- **Возврат переплаты (`overpayment`) и проверка статуса:** перейдите в **Stores → Configuration → Sales → Payment Methods → Paymos**, введите ID заказа в блоке **Paymos refunds**, нажмите **Load order** и выберите **Refund overpayment** либо **Check full refund** / **Check overpayment refund**.

Magento создаёт Credit Memo и добавляет запись в историю заказа только после того, как Paymos подтвердит статус `completed` через `/paymos/payment/callback`, ручную проверку статуса или ежеминутную задачу `paymos_reconcile_refunds`. В режиме Sandbox финальные исходы возврата (`completed`, `failed`, `cancelled`) можно симулировать без отправки переводов в сеть.

## Решение проблем

**Paymos не появляется при оформлении заказа.** По умолчанию способ оплаты выключен. Включите **Enabled** (Yes) на уровне того веб-сайта, к которому относится витрина, убедитесь, что **Connection status** показывает подключение, и сбросьте кеш конфигурации — Magento кеширует `payment/paymos/*` наравне с остальными настройками.

**Заказы застряли в статусе ожидания оплаты.** Не доходит вебхук. Адрес обратного вызова должен быть доступен из публичного интернета ровно по тому базовому URL, который вы подтверждали: loopback, частные и link-local адреса блокируются, а редиректы не отслеживаются. Если магазин переехал на другой хост или появился редирект, подключите модуль заново. Команда `bin/magento cron:run` покажет, сможет ли задача сверки закрыть разрыв тем временем.

**Подключение падает с ошибкой "Magento base URL must use HTTPS".** Авторизация устройства берёт базовый URL витрины по умолчанию — именно он показывается на экране подтверждения и уходит в регистрацию вебхука. Переведите его на HTTPS и запустите подключение снова.
